Why it went unnoticed: a fresh database looks perfect, because schema.sql already carries the end state — a column-level diff showed zero differences. But the 31 skipped files contain 19 ALTER TABLEs and 42 data backfills: the only mechanism by which an existing database (production, shadow) ever evolves. Migrations run automatically on deploy.

For the roomThis is the finding that reframes the audit: the schema we all measure locally is not provably the schema production has. It's also a one-line fix — scope the catch to step 1 — plus an IF NOT EXISTS on 010.

Critical  API-1 — The rate limiter is sized for pages, but the SPA spends requests

Benchmark proof: the first load-test run produced 511,872 responses in 30 seconds — every one an HTTP 429. The limiter, not the application, is the binding constraint. Worse, the client treats 429 as a permanent failure: a throttled PATCH of document metadata — title, state, assignee — is silently dropped, surfacing only as a toast. Editor body text survives (the WebSocket path bypasses the limiter); metadata writes do not.

For the roomNo latency work is observable in production until this is fixed — the limiter caps throughput two orders of magnitude below what we measured the app can do. Key it per session, size it per page-view reality, and make the client retry 429s with backoff.

Critical  ERR-1 — A collaboration socket that never connects loses edits under a “Saved” label

web/src/components/Editor.tsx (sync indicator) · api/src/collaboration/index.ts · reproduced via WebSocket fault injection

When the /collaboration WebSocket is unreachable at editor load but HTTP is alive, the editor keeps accepting edits under a reassuring “Cached / Saved” indicator, never completes the initial Yjs sync, and discards the work on reload — final DB content empty, no warning. Whole-browser-offline recovers cleanly; this collab-socket-only case does not.

For the roomThe indicator maps “I have a local cache” to “Saved.” The fix is to make it tell the truth — a distinct “not syncing” state that blocks the false “Saved.” This is the mandatory data-loss fix of the improvement phase.

Critical  ERR-2 — Session revocation is not enforced on live collaboration sockets

api/src/collaboration/index.ts:659 (auth at WS upgrade only) · :718–745 (per-message handler never re-checks)

The socket is authenticated once, at connection. After the session is deleted or expired server-side, the open editor keeps writing to documents — verified: post-revocation edits persisted, and again 60 seconds later. A logged-out or revoked user retains write access until the socket happens to close.

For the roomAuth is a connect-time gate, not an ongoing check. Re-validate the session periodically on the socket and close it on failure — the same change lands next to ERR-1 in one file.

Error handling 9 findings · 2 Critical, 2 High

Fault injection across disconnect, concurrency, malformed input and slow network. The happy path is clean — zero console errors across 8 flows, no exploitable XSS, clean API validation — but four write-failure modes are silent, and two are Critical (ERR-1, ERR-2, above).

  • ERR-3High Rejected writes (429/500 PATCH) are silently dropped while the sync indicator still reads “Saved” over the unsaved value.A transient toast fires; the persistent indicator contradicts it, and users trust the wrong half.
  • ERR-4High Editing a document deleted elsewhere continues with no notice; post-delete edits vanish.The editor holds a live surface over a document the server has already removed.
  • ERR-5Med Invalid path/query params return 500 instead of 400/404 — bad uuid/enum reach Postgres directly.Also ERR-6 (comment orphan) · ERR-7 (no loading state, 61s 3G page) · ERR-8/9 (unbounded limit, console noise) in the index.
For the roomThe pattern from cause #1 again: writes fail quietly. The three worth shipping are ERR-1, ERR-2, ERR-3 — all “make the failure loud.”

iv.

The defense: three systemic causes

Forty-five findings, but not forty-five problems. Nearly everything above traces to three architectural habits — which is good news, because habits can be fixed centrally.

  • 1 · Failures are silent by default. The migration runner exits 0 having done a quarter of its job. Retries convert failing tests to green. Vacuous tests pass on missing data. pnpm lint matches zero targets and succeeds. Dropped 429 writes surface as a toast.Pattern: every guard rail reports success on the path where it did nothing. Defense priority #1 is making failure loud — CI, scoped catches, retry budgets, assertion linting.
  • 2 · Shared mechanisms concentrate cost. One auth middleware taxes every request with three queries and a write. One entry chunk taxes every page with the whole app. One untyped pg pool taxes every route with unchecked rows. One rate-limit key taxes a whole agency NAT.Pattern: the unified architecture that makes Ship elegant means single-point fixes have system-wide yield — throttle one write, lazy-load one component, type one pool.
  • 3 · Nothing ratchets. No CI, no lint, no bundle budget, no coverage gate (the tool isn't even installed), a stale test-count comment 228 tests out of date.Pattern: every improvement made this week can silently regress next week. The remediation plan pairs each fix with the ratchet that keeps it fixed.

The same bug from two angles. Five pairs of findings share a single root cause — fix the root once and both resolve. Trace this when a finding ID looks isolated:

  • ERR-1 ↔ ERR-2 both live in the collaboration server (data loss + session enforcement) — one file, one fix window.
  • DB-2 ↔ API-6 the same per-request UPDATE sessions write, seen from the query trace and the endpoint benchmark.
  • DB-4 ↔ API-4 / API-5 the same week-dashboard standups fan-out (client N+1) — and the cause of the 61-second slow-network main page (ERR-7).
  • API-2 ↔ DB-5 the same /api/issues list shipping the full document body the list UI never reads.
  • ERR-6 ↔ TEST-5 the same orphaned comment-highlight-on-cancel bug — TEST-5 is the failing test that reproduces it.
