Phase 1 — the system & its findings

What Ship is, and where it hurts

Six maps. The first three are the machine as designed; the last three are where the audit found damage. Trace them in order — each one reuses nodes from the one before.

1.1 The system in one map

One React SPA, one Express API, one Postgres table doing most of the work. "Everything is a document" — wiki, issue, project, sprint, person, weekly_* all live in a single documents table, distinguished by a document_type column, not by separate tables.

1.2 The request path — and the write hiding in every read

Every authenticated request walks the same middleware. The trap the audit found lives here: every request — even a plain GET — issues a session-row UPDATE plus two reads before the route even runs. That auth boilerplate is 52–94% of all queries per flow (DB-2 / API-6, same root cause).

1.6 Infrastructure topology (Terraform)

The IaC is AWS, not Render — Elastic Beanstalk + Aurora Serverless v2 in a VPC, fronted by CloudFront/S3 + WAF, secrets in SSM. Well-secured, but two foot-guns: only the state bucket is protected from deletion (TF-1), and two divergent root configs describe the same infra (TF-2).

Phase 2 — testing, build & deploy

How it's tested, packaged, and shipped

Answers to items 6 & 7, drawn the same way. The through-line: the machinery is careful (isolated per-worker envs, memory-aware) but there is no CI gate and the build happens on a laptop, not in the image.

2.6 Testing infrastructure

Structure. Playwright's testDir is e2e/ — 869 e2e tests across 71 spec files, plus 602 unit tests (451 api + 151 web) under vitest. A global-setup.ts builds the API and Web once up front, so each worker can serve the built app with a lightweight vite preview instead of a memory-hungry dev server.

Fixtures (e2e/fixtures/isolated-env.ts) are worker-scoped and chained — each layer depends on the one before:

  • Setup / teardown: each worker spins a fresh Postgres 15 testcontainer (retried 3× for port congestion), runs migrations, then tears it down in a finally via container.stop() — so the DB never leaks between runs. API + web procs are likewise killed in finally.
  • The memory lesson (baked into a comment): vite dev = 300–500 MB/worker (HMR, watchers) vs vite preview = 30–50 MB. Workers default to 4 (~2 GB); sizing is memory-aware (~500 MB/worker).
  • A quiet skew to remember: e2e uses postgres:15 (testcontainers) while docker-compose declares postgres:16. The context fixture also disables the "Action Items" modal via a localStorage flag.

2.7 Build & deploy

The Dockerfile produces an API-only runtime image — and, crucially, it does not build the app. It starts from public.ecr.aws/.../node:20-slim (ECR, because Docker Hub is blocked in gov environments), installs production deps only, then COPYs pre-built shared/dist and api/dist that you compiled locally first. It exposes port 80 and its CMD runs migrations, then the server:

Because migrations run on container boot, the DB-1 "silently skips migrations" bug ships straight into the deploy path. Dockerfile.web and Dockerfile.dev are dev-only (Vite dev server), used by compose — the frontend is not in the runtime image; it deploys to S3/CloudFront separately.

docker-compose — two files, both optional (the recommended dev DB is native Postgres):

Terraform providers & pinning. required_providers pins hashicorp/aws ~> 5.0 and hashicorp/random ~> 3.6 — version-constrained, and the modules + environments/prod commit lock files. Two gaps: the flat root has no committed lock (TF-4), and the pinned Terraform 1.6.0 can no longer init at all — its bundled signing key has expired (TF-3). Week-4 direction: keep the local provider for exercises, add the render-oss/render provider for deploys — no AWS account needed.

CI/CD: there isn't a pipeline. There is no .github/workflows/ — only a Codacy static-analysis instructions file. Nothing runs the test suite automatically (that's the teeth behind TEST-1). Deploys are manual scripts:
