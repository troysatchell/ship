01 · Overview

The boundary is the architecture.

Ship is getting a front door for outside developers — separate from the door our own app uses, but both open into the same core. Every check happens at that front door, one step at a time: who you are, what you're allowed to do, how fast you can go, and a record of what you did. Each step stands alone, so each can fail clearly and be tested on its own.

02 · Decisions

Every decision, with the alternative it beat.

OAuth
Built by hand, kept minimal
We built the sign-in-for-apps system ourselves from the official standard, keeping only the parts we need. It's small enough to hold in one head — and to defend line by line.
Off-the-shelf server — faster to working, but understanding the contract is the graded skill, and you can't defend a black box.
Public resources
Three clean shapes over one store
Inside Ship, everything is one kind of record. Outside developers see three purpose-built shapes instead — documents, issues, sprints — easier for them, unchanged for us.
Expose the raw storage — honest to how it works, hostile to the people who'd have to use it.
Webhook engine
Queued in memory, written down always
Deliveries queue in memory, but every attempt is written down — so the history, the failures, and the replay button all survive a restart. A heavier queue can drop in later without touching anything around it.
Industrial queue on day one — new infrastructure in a one-week sprint is risk without payoff.
Signing secrets
Locked, not scrambled — on purpose
The brief asks for these secrets stored in a form that would make them unusable — a seal can only be made with the actual secret. So we store them locked, show them exactly once, and say so. Stripe does the same.
Written up openly in the architecture doc — a deviation defended beats a requirement faked.
SDK
Hand-written, drift-checked
The developer toolkit is written by hand for quality — and on every change, a test compares it against the API's published spec. If they ever drift apart, the build fails.
Auto-generated toolkit — can never drift, but reads like a machine wrote it. The drift test buys the same safety without that cost.

03 · Security mechanics

Flows that fail correctly.

Sign-in · web apps
01The app starts sign-in with a one-time puzzle only it can answer.
02You approve on a real Ship page — one that can't be embedded or faked.
03The approval code lives ten minutes and works exactly once.
04To get real keys, the app must answer its own puzzle. Wrong answer — everything it was issued is thrown away.
Terminals sign in differently: the CLI shows a short code, you approve it in a browser, and it patiently polls — slowing down when told to.
Stolen keys · reveal themselves
01Keys expire after an hour. Renewal keys work exactly once.
02Each renewal mints the next key in the same family line.
03If an old key is ever used again, two people must be holding it — the whole family dies and everyone signs in fresh.
This isn't a claim — the stolen-key story runs as a test in our suite, end to end, on every change.
Deliveries · sealed
01Every delivery carries a seal made from its exact contents plus the moment it was sent — Ship-Signature: t=…,v1=…
02Change one character in transit and the seal breaks.
03A captured message dies in five minutes — replaying it later gets you nothing.
04The receiver checks all of this with one helper call, in under a millisecond.
Delivery discipline
1s→4s→16s→1m→5m→30m→DLQ
Failed deliveries retry on this schedule. Permanent failures park in a holding pen — visible in the portal, replayable with one click — and the receiver can always tell a replay from an accident.

04 · Agent as platform citizen

The agent walks in the front door.

Last week's AI assistant reads Ship through a private back door only our own code can use. This week the back door closes: the assistant signs in like any outside app, with read-only access — and when it writes, it writes as the human who approved it, never as itself. A switch flips between old and new, and the tests pass both ways.

Before · privileged insider
agent ─ X-Internal-Secret ─→ internal /api
└─ minted tokens, no scopes,
    no rate limits, invisible to audit
A back door. It works — but it proves nothing about the platform.
→
After · hybrid citizen
reads  ─ ship_app_fleetgraph · client credentials
         read-only scopes ─→ @ship/sdk ─→ /api/v1
writes ─ the accepting human's scoped token
         per accepted draft ─→ @ship/sdk ─→ /api/v1
The old rule survives: the AI can never write on its own — still proven by tests — and every write belongs to a person.
The payoff is one search of the logs: everything the assistant did sits there looking exactly like any outside developer's activity — same permissions, same speed limits, same paper trail. What it cost: a registered app, a toolkit dependency, and a switch. What it bought: the assistant is now proof the platform works, not an exception to it.

05 · Infrastructure & blast radius

Terraform is the truth. Here's how I read it.

Topology · terraform/render

Proof sequence
01The full plan is printed, annotated by hand, and committed before anything deploys.
02We change one thing by hand in the dashboard — the plan catches us.
03Then we destroy everything and rebuild from the config alone. It comes back identical, seeded apps and all.
Said honestly: our host has no AWS-style roles. The same idea — least privilege — maps onto what it does have: scoped keys, isolated services, sealed secrets. What it can't express is written down. A trade we defend, not a gap we hide.
