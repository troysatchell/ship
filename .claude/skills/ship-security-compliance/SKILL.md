# Security compliance

## The absolute rule

**Never `git commit --no-verify`.** The pre-commit hook is this repo's secrets scan. Bypassing it is
a security-compliance violation, not a shortcut, and the bypass leaves no trace in the commit for a
reviewer to notice.

When a hook fails, **fix the cause**. If you believe the hook is wrong, that is an escalation — say
so and stop, rather than routing around it.

## What pre-commit actually runs

`.husky/pre-commit`, three checks in order:

**1. `scripts/check-empty-tests.sh`** — fails on Playwright tests whose bodies contain no `expect()`
or `page.` call. Empty tests report as passing; 68 e2e tests in this repo did exactly that (finding
TEST-2). Fix by using `test.fixme()` for anything unimplemented, which reports as skipped — honest.
`test.skip` and `test.todo` are also excluded from the check.

**2. `scripts/check-api-coverage.sh --staged`** — scans staged `.ts/.tsx/.js/.jsx` files for new UI
routes and verifies a corresponding API endpoint exists. Exits 1 on missing coverage. If it fires,
either the endpoint is genuinely missing (add it — see `/ship-openapi-endpoints`) or the UI route
does not need one, which means the heuristic misread your change and needs a written reason.

**3. `comply opensource --hook --staged --exclude e2e --skip-trivy`** — the Treasury
compliance-toolkit scan: secrets detection plus AI analysis. `--skip-trivy` is a **documented
temporary workaround** for an `ImportError` in the toolkit's sbom module; the hook comments it as
such. Do not remove it casually and do not add other `--skip-*` flags to get a commit through.

### The gap you must know about

If `comply` is not on `PATH`, the hook **prints a warning and lets the commit proceed**. The `else`
branch echoes "WARNING: 'comply' CLI not installed" and exits 0.

**Observed 2026-07-29: `comply` is not installed on this machine** (`command -v comply` → nothing).
So on this checkout, commits are passing checks 1 and 2 and *skipping the secrets scan entirely*,
with only a warning in the output.

Two consequences:

- **A successful commit here is not evidence the compliance scan passed.** If you report a commit as
  "compliance-checked", say whether `comply` was actually present. This is the same failure class as
  the container smoke test that passed *because* it skipped the broken code path.
- Install it before committing anything sensitive: `pip install comply-cli`. `package.json`'s
  `postinstall` prints the same warning on every `pnpm install`, which is easy to scroll past.

## CI enforcement

`.github/workflows/ci.yml` runs on push and PR, two jobs:

- **`verify`** — typecheck, build, migrate the CI database, api unit tests, web unit tests, then
  compare failures against `audit/factory/quarantine.json` by identity. Uploads both JSON reports as
  artifacts.
- **`inventory`** — source-code inventory, uploaded as an artifact.

**CI deliberately omits `pnpm lint`.** No package defines a `lint` script and there is no ESLint
config anywhere (finding TS-6), so the command exits 0 having checked nothing. Running it would make
CI advertise a quality gate that does not exist. If you add ESLint, add the CI step in the same
change — not before.

## Supply chain conventions in CI

- **Third-party actions are pinned to a full commit SHA** with the version in a trailing comment:
  `uses: pnpm/action-setup@b906affcce14559ad1aafd4ab0e942779e9f58b1 # v4`. A mutable tag on a
  third-party action is a supply-chain hole — the tag can be repointed.
- First-party `actions/*` (checkout, setup-node, upload-artifact) are referenced by major tag.
- Match the existing convention when adding a step. If you add a new third-party action, resolve its
  SHA and pin it.

## Secrets

- Nothing secret in the repo. Local dev uses `api/.env.local` (generated by `scripts/dev.sh`).
- Production configuration comes from AWS SSM / Secrets Manager (`@aws-sdk/client-ssm`,
  `@aws-sdk/client-secrets-manager`). Note that `api/src/config/ssm.ts:39` returns early under
  `NODE_ENV=development` — a smoke test run in development skips the retrieval path entirely and
  proves nothing about production. State the `NODE_ENV` any config test ran under.
- **Rotating a credential is a stop-for-human action**, every time, even if a similar rotation was
  approved earlier.

## When a check fails

| Check | Do this |
|---|---|
| `check-empty-tests.sh` | Convert the stub to `test.fixme()`, or implement it. Never delete the check. |
| `check-api-coverage.sh` | Add the endpoint, or write down why the UI route needs none. |
| `comply opensource` | Read what it flagged. A real secret: remove it, rotate it, and treat the rotation as an escalation. A false positive: fix the pattern or narrow the exclusion **in the hook**, in its own commit, with the reason. |
| `comply` missing | `pip install comply-cli`. Do not treat the warning as a pass. |

Never resolve any of these with `--no-verify`.
