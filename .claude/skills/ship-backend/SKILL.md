# Ship backend

Read this before touching `api/`. The factory's agent contract tells you how to prove a fix; this
tells you what is true about this backend.

## Stack, as it actually is

| | |
|---|---|
| Server | Express 4, TypeScript, `tsx watch` in dev, compiled to `dist/` for prod |
| Database | PostgreSQL via **`pg` directly — no ORM, deliberately**. Raw SQL, parameterized |
| Validation | `zod`, shared with the OpenAPI generator via `@asteasolutions/zod-to-openapi` |
| Realtime | `ws` + `yjs` / `y-protocols` — `api/src/collaboration/index.ts` |
| Auth | `express-session` + cookies, `bcryptjs`, `csrf-sync`, `openid-client`, `helmet`, `express-rate-limit` |
| AWS | SSM, Secrets Manager, S3, Bedrock (`@aws-sdk/*`) |
| Tests | Vitest + **supertest**, `include: ['src/**/*.test.ts']`, `fileParallelism: false` |

`pnpm lint` is a no-op — no package defines a `lint` script and there is no ESLint config
(finding TS-6). It exits 0 having checked nothing.

## The unified document model

One `documents` table with a `document_type` discriminator (wiki, issue, program, project, sprint,
person). Content types differ by **properties, not structure**. Do not add a content table; a
"new type of thing" is a new `document_type` plus properties.

Relationships go through the `document_associations` junction table (`parent`, `project`, `sprint`,
`program`).

**The legacy association columns are gone.** `documents.sprint_id` and `documents.project_id` were
dropped by `027_drop_legacy_association_columns.sql`, `documents.program_id` by
`029_drop_program_id_column.sql`. Do not write code against them.

Two traps around that:

- `sprint_iterations.sprint_id` (`api/src/db/schema.sql:272`) is a **different column on a
  different table** and is live. Don't confuse them.
- `pnpm db:migrate` **exits 0 while under-applying** (finding DB-1 — it abandons around migration
  010). So a given database may not have run 027/029. Exit 0 does not mean 42 migrations applied.
  Confirm with `\d documents` before relying on a column's absence — or its presence.

Why a fresh deploy still works, and why the obvious inference is wrong: `api/src/db/migrate.ts:38-41`
applies `schema.sql` **first**, so a brand-new database comes out complete. DB-1 is not a
fresh-deploy blocker; it is an existing-database drift problem. This exact claim was stated
backwards once in this project while the audit report had it right.

## Every new route must be registered with OpenAPI

Two files, always, or the endpoint is invisible to Swagger and to the generated MCP tools:

1. **Schema + path registration** in `api/src/openapi/schemas/<resource>.ts` — define the zod
   schemas, then `registry.registerPath({ method, path, tags, summary, request, responses })`.
   Pattern to copy: `api/src/openapi/schemas/issues.ts:233` (list with query filters) and `:269`
   (get by id with `params`). Reuse `UuidSchema` and friends from `schemas/common.ts`.
2. **The route itself** in `api/src/routes/<resource>.ts`.

The registry is global (`api/src/openapi/registry.ts`) and the document is generated by
`pnpm --filter @ship/api openapi:generate`. Security schemes (`bearerAuth`, `cookieAuth`) are already
registered there — reference them, don't redefine them.

`/ship-openapi-endpoints` has the full three-file walkthrough, including the `/api` server-prefix
rule and why `summary`/`description` decide whether the generated MCP tool is usable. Read it before
adding an endpoint; copy the nearest existing schema file either way.

Note the path convention: `registerPath` uses `/issues`, not `/api/issues` — the prefix is applied
when the app mounts the router. Copy a neighbour rather than guessing.

## Migrations

```
api/src/db/migrations/NNN_description.sql
```

- **Never edit `schema.sql` for an existing table.** It is initial-setup only. Every change to an
  existing table is a numbered migration.
- Applied automatically on deploy by `api/src/db/migrate.ts`; tracked in `schema_migrations`; each
  runs in a transaction with rollback on failure.
- Adding an index for a query fix **is** a migration. An index created by hand in a psql session
  exists on your machine and nowhere else, and the measured improvement will not reproduce.

## SQL discipline

- **Always parameterize values.** `$1`, `$2` — never string interpolation.
- **Identifiers cannot be parameterized.** Table, column, and database names have to be
  interpolated, so they must be **validated against an allowlist or a strict regex first**. This
  is not theoretical here: CodeRabbit caught an unvalidated ticket ID reaching `CREATE DATABASE`
  in the factory's own provisioner.
- **N+1 is the dominant finding class** in the DB category. A loop containing `await pool.query`
  is the shape to look for. Fix by joining or by a single `WHERE id = ANY($1)`.
- Prove a query fix with `EXPLAIN ANALYZE` before and after, and say which database and what data
  volume it ran against. The baseline used `postgres:15-alpine` on the Docker container at `:5433`
  with 500 documents / 100 issues / 20 users (`audit/shipshape.config.yaml`).

## Auth and sessions — a stop-for-human zone

`api/src/middleware/auth.ts` enforces two windows from `@ship/shared`: `SESSION_TIMEOUT_MS`
(inactivity, checked at `:169`) and `ABSOLUTE_SESSION_TIMEOUT_MS` (checked at `:155`), with the
cookie `maxAge` re-set at `:218`.

Changes to session semantics, CSRF, cookie flags, or the collaboration server's authorization path
**escalate before merge** — a passing test still leaves room for an expensive mistake. ERR-2
(revoked sessions retaining socket write access) is in exactly this area. See escalation gate 6 in
`ship-factory/references/escalation.md`.

## The collaboration server

`api/src/collaboration/index.ts` handles the Yjs sync protocol over `ws` at
`/collaboration/{docType}:{docId}` and persists CRDT state to `documents.yjs_state`.

- It owns `yjs_state` for any doc with a live session. A REST write to `content` while a session is
  open will be overwritten by the next sync.
- ERR-1 and ERR-2 both live in this file and are one change — one branch, not two parallel ones
  that conflict.
- Socket-path errors do not surface as HTTP 500s. Check for unhandled rejections and connection
  teardown, not just status codes.

## Testing — and the hazard that eats databases

`api/src/test/setup.ts` runs `TRUNCATE TABLE ... CASCADE` across **16 tables** in the `beforeAll`
of **every** api test file — workspaces, users, documents, sessions, audit_logs and more.

- **Never run `pnpm test` with `DATABASE_URL` unset or pointing anywhere you care about.** In a
  factory worktree, `source .factory-env` first; that is why every ticket gets its own database.
  `scripts/factory/gate.sh:51-57` refuses to run unless the URL looks factory-owned.
- `fileParallelism: false` is deliberate — the truncation makes concurrent files destroy each
  other. Do not "speed up the suite" by turning it on.
- Route tests use **supertest** against the Express app; put them beside the route as
  `api/src/routes/<resource>.test.ts` (that convention is already dense — `documents.test.ts`,
  `issues.test.ts`, `auth.test.ts`, …). Utility tests go in `__tests__/` next to the util.
- Root `pnpm test` runs **api only**. Web needs `pnpm --filter @ship/web test`.

## Measurement caveats that change the number

The canonical short list is `ship-factory/references/lessons.md` (§Measurement) — edit it there
first; these two are repeated here because they decide whether a backend fix reads as an improvement
at all.

- `/api-perf-audit compare <label>` for latency; **`/db-query-audit` must run after it, never
  concurrently** — the statement logging it enables skews api-perf's timings.
- **gzip shows no win on loopback** (API-3). Measure payload bytes, or use a shaped link, or the
  compression fix reads as no improvement.
- Report steady-state numbers, note cold-start separately, and revert any logging configuration you
  changed — and say that you reverted it.
